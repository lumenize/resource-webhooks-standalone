# SEP notes

The requirements of the SEP this prototype will become, in RFC 2119's words: MUST, SHOULD and MAY. Each gets a number that is never reused, so a conformance traceability file can cite it. The scenarios in `tasks/master-plan.md` show most of them at work, and each names the ones it shows.

These notes are for the design's second level, resource state sync. The first level, `mcp.resource.updated` over Events, needs nothing beyond SEP-3415 and the type its Open Question 2 sketches, so it adds no requirement here. It shares A's webhook code with the second level, and with it N3, within SEP-3415's room.

## Departures from SEP-3415

**This extension takes SEP-3415's webhook delivery by reference, and goes against its text in one place.** Each departure says what it needs from Peter.

- **D1. The reserved header and well-known paths are reused (R17).** SEP-3415 reserves them for Events: "The HTTP header `X-MCP-Subscription-Id`, and the well-known paths `/.well-known/mcp-webhook-receiver.json` and `/.well-known/mcp-webhook-jwks.json`, are reserved for this extension." Resource webhooks uses all three, with the meanings SEP-3415 gives them. Read as barring other meanings, the reservation allows that, and read as barring other uses, it does not. Reuse lets one receiver, with one receiver document on its origin, serve both extensions without telling their deliveries apart, and SEP-3415's own wording is general: its receiver document declares paths that accept "MCP webhook deliveries", and "MCP webhook delivery is a profile" of Standard Webhooks. It needs Peter to agree that the reservation bars other meanings, not other uses. If he does not, this extension names a header and paths of its own, and a receiver that serves both handles two sets. The JWKS path may yet go: SEP-3415 is still choosing between it and SEP-2127's server cards as the place to publish the optional signing key (Clare Liguori, 2026-10-19, and Peter, 2026-10-23, on its thread).

## Narrowings of SEP-3415

**Where SEP-3415 leaves a server room, this extension makes a choice within it.** None of these conflicts with SEP-3415's text:

- **N1. Coalesced retries, in order per URI (R12, R13).** SEP-3415 describes retrying each event independently, with deliveries that may arrive out of order. It requires neither: it caps retries, sets no minimum, and lets a server abandon a delivery. Here a newer version replaces a pending older one, so a URI's deliveries arrive in version order. Peter agreed on SEP-3415's thread, on 2026-10-16, that an event type may coalesce, and that coalescing should not set `truncated`.
- **N3. The subscription `id` is a keyed hash (R25),** where SEP-3415 asks only that it be deterministic.
- **N4. A body too large for the `full` form goes as `notify` (R27),** keeping every body within SEP-3415's 256 KiB delivery profile.
- **N6. Contents travel only on request (R5, R10).** SEP-3415's § *Payload minimality* says "Servers SHOULD keep event payloads minimal: enough to identify and triage the event, and not the full content." The default form, `notify`, does, naming only the resource and its version. A subscriber that asks for `full`, for its deliveries or for a catch-up, gets the contents, because sparing it a read is the point of resource state sync, and a server need not offer `full` at all (R1). A SHOULD leaves room for a reason that is understood, and here the subscriber gives it by asking. SEP-3415's own Open Question 6 sketches a task event whose payload may carry the task's `result`.

## The capability

- **R1.** A server that offers this extension MUST declare `io.modelcontextprotocol/resource-webhooks` in `capabilities.extensions`, with a settings object whose `forms` lists the forms it delivers. `notify` MUST be among them.
- **R2.** A client MUST NOT call this extension's methods on a server that has not declared it.

## Versions

- **R3.** A resource that a server accepts subscriptions to, other than a collection (R38), MUST have a version: an opaque string that changes whenever the resource's contents change, and is never reused for the same URI, with the semantics of HTTP's `ETag`. Clients MUST compare versions only for equality. Versions are not required to sort in time. A server whose versions do sort MAY rely on that in its own implementation.
- **R4.** For a resource that R3 covers and that has an `https` URI, the version MUST be the characters between the quotes of the resource's strong `ETag`, so that a client can send it, quoted, in `If-None-Match`.
- **R37.** A server MUST answer for a resource with no version, one never written or one whose deletion it no longer keeps, as R11 answers for a deletion, at a base version the server mints.
- **R47.** For a resource that R3 covers, a server MUST give each entry of a `resources/read` result's `contents` whose `uri` is not `https` the resource's version in `_meta`, under the key `io.modelcontextprotocol/resource-webhooks.version`, provisional until one is agreed (§ *Pending*). It SHOULD do the same for an entry whose `uri` is `https`, so that a client reading it through MCP can tell whether it read the version a delivery named.

## Subscribing: `resources/webhooks/subscribe`

- **R5.** The request carries exactly one target (`uri`, `uriTemplate`, or `listed: true`), an optional `form`, an optional `version` naming the version the client holds of the resource a `uri` target names, an optional `cursor` for a collection (R32), an optional `catchUp` naming the result's form, `delivery` with `url` and `secret`, and an optional `ttlMs`. A request without `form` gets `notify` deliveries, and one without `catchUp` gets a `notify` result. The two are independent. A `form` it names MUST be one the server declared.
- **R6.** The subscription key is `(principal, delivery.url, target)`, with `delivery.url` compared as an exact string, and the target compared as its kind and its value (`uri`, `uriTemplate` or `listed`). A request whose key matches an existing subscription refreshes it: the server grants a TTL again, and replaces `form` and `delivery.secret`.
- **R7.** A server MUST refuse a `uri` it could never serve, such as one with a scheme it does not serve or one outside all its templates, with the error `resources/read` gives for it. A `uri` that names a deleted resource is not refused, by R11. It MUST refuse a `form` it did not declare with SEP-3415's `Unsupported`, with `data` `{"feature": "form", "value": ...}`, and a `catchUp` likewise, with `"feature": "catchUp"`.
- **R8.** The result MUST carry `id` and `refreshBefore`. For a `uri` target naming a resource that is not a collection, it MUST also carry that resource's current `version`, with `deleted: true` when that version deleted it, and, when the request's `catchUp` is `full` and its `version` is absent or differs, the resource's `contents`, as `resources/read` would return them. For a collection, it carries what R32 to R35 say.
- **R40.** A request to either method MUST carry an `Mcp-Name` header holding its target's `uri` or `uriTemplate`, as the transport's rule for `resources/read` takes `params.uri`. A `listed` target carries none.

## Delivering a change

- **R10.** When a resource the subscription covers changes, the server MUST deliver a `ResourceChange` with that resource's `uri`, the `form` and its new `version`. In the `full` form, the delivery MUST also carry `contents` (N6).
- **R11.** When a resource the subscription covers is deleted, the server MUST mint a version for the deletion, like any other version, and deliver `{"uri": ..., "form": "notify", "version": ..., "deleted": true}`, whatever the subscription's form. The subscription MUST carry on.
- **R12.** A server MUST keep at most one delivery in flight per subscription and URI. When a newer version of a resource lands while an older one is pending or being retried, the server MUST deliver the newer one in its place (N1).
- **R13.** A server MUST NOT deliver a version of a resource after delivering a newer one to the same subscription. It MAY skip intermediate versions (N1).
- **R14.** One message, in SEP-3415's sense of `webhook-id`, is one version of one URI on one subscription. Its `webhook-id` is the same for every retry, and a newer version that replaces a pending one is a new message, with a new `webhook-id`.
- **R15.** A client SHOULD ignore a delivery naming a version it already holds, and SHOULD pass the version it holds of the resource a `uri` target names in `version` on every refresh.
- **R26.** A `ResourceChange` MUST NOT carry a top-level `type`, so that SEP-3415's rule tells it apart from a control envelope.
- **R27.** In the `full` form, a server MUST deliver a change in the `notify` form instead when its body would exceed the 256 KiB bound that SEP-3415's delivery profile recommends (N4).
- **R28.** A receiver's `410 Gone` stops the server retrying that version only, as SEP-3415 leaves the subscription unaffected. The server MUST still deliver the resource's later versions (R17).
- **R30.** A receiver that acts for a client, as a gateway does in SEP-3415's forward-proxy deployment, MUST make each `ResourceChange` it accepts available to that client whole, as SEP-3415 requires of `cursor` and `eventId`.
- **R31.** A client that may have missed deliveries, for example because its gateway could not reach it, SHOULD refresh each of its subscriptions.
- **R41.** A client that receives a delivery for a URI while a refresh naming it is outstanding SHOULD refresh again once that result arrives, since the result and the delivery travel apart and either may arrive first.

## Unsubscribing: `resources/webhooks/unsubscribe`

- **R16.** The request carries the target and `delivery.url`, which with the caller's principal identify the subscription. The result is empty. A request that matches no subscription is refused with SEP-3415's `NotFound`, with `data.kind` `"subscription"`.

## Taken from SEP-3415 by reference

- **R17.** Webhook delivery follows SEP-3415's § *Webhook-Based Delivery*, at commit b0efd11, with these substitutions: this extension's methods for `events/subscribe` and `events/unsubscribe`, R6's key for SEP-3415's subscription key, a `ResourceChange` for an `EventOccurrence`, a change's `uri` and `version` for an event's `eventId`, and one version of one URI for the delivery that SEP-3415's `410` rule stops, so later versions still go (R28). It also takes SEP-3415's § *Authorization* by reference, re-verifying at delivery time, with the target in place of an event type and its arguments, and R39 adds what that means for a collection. Everything else is narrowed as N1, N3, N4 and N6 say. SEP-3415's `cursor`, `maxAgeMs`, `truncated` and `gap` envelope never apply: one resource needs only its version, and a collection uses this extension's own `cursor` (R32 to R35), with `reset` (R34) in place of `truncated`.
- **R29.** This extension uses SEP-3415's general-purpose error codes as SEP-3415 defines them: `Forbidden` for a principal refused or missing, `ResourceExhausted` for a server limit, `CallbackEndpointError` for a callback that fails verification or cannot be reached, plus `Unsupported` (R7) and `NotFound` (R16). On a server that requires a token, a missing principal never reaches a method, since the transport answers `401` first.
- **SEP-3415's § *SSRF prevention* is met by the platform on Cloudflare Workers, as far as two measurements show.** SEP-3415 asks a server to check a callback's resolved address at delivery time and connect to that address. A Worker's `fetch()` can do neither, since it takes no address and offers no DNS lookup.
  - **Measured on 2026-10-25 through A's own delivery path:** each subscribe's handshake was A's `https` POST from a Durable Object, at compatibility date 2026-10-01 with `global_fetch_strictly_public`, to a name sslip.io or nip.io resolves to one address. A first run had fetched `http://` from a Worker's fetch handler, and every special-purpose address got the same answer both ways.
  - **Refused by Cloudflare,** with a page of its own naming an error code. 1016: 127.0.0.1, 10.0.0.1, 172.16.0.1, 192.168.0.1, 169.254.169.254, 0.0.0.0, 255.255.255.255, `::1`, `fc00::1` and `fe80::1`. 1002: 100.64.0.1, 198.18.0.1, 198.51.100.1, 203.0.113.1, 224.0.0.1, 240.0.0.1, `2001:db8::1`, `64:ff9b::a00:1` and `::ffff:127.0.0.1`. 1003: 10.0.0.1, 127.0.0.1 and `localhost` named directly, as an IP literal or `localhost` gets. Cloudflare's docs call 1016 an origin DNS error and 1002 a name pointing to a prohibited IP. That Cloudflare refuses these before it connects is inferred from the codes, not measured.
  - **Reached:** Google's address through both services, and 1.1.1.1, each answering `526`, Cloudflare's code for a certificate that does not match the name, so the connection was made. Over `http`, 1.1.1.1 had got 1034.
  - **Three addresses went out and timed out:** 192.0.0.1 and 192.0.0.8, in 192.0.0.0/24, and 192.0.2.1, in 192.0.2.0/24. SEP-3415's SHOULD covers both ranges.
  - **Rebinding reached no private address.** 1u.ms names, a new one for each fetch, answer Google's address to their first query and 10.0.0.1 to every later one. In four runs of 12 fetches, 7, 8, 6 and 4 reached Google, and every other fetch was refused with 1002. So in some fetches a lookup got the private answer, and Cloudflare refused it. The runs do not show why a lookup got it: an AAAA query or a second resolver's retry may have used up the first answer, or Cloudflare may resolve again as it connects. The first run's alternating name, which reached Google on all 14 fetches, showed nothing either way.
  - **The Worker fetches with `redirect: "manual"`,** and treats any `3xx` as a failed delivery, since SEP-3415 forbids following one.
  - **For the PR: SEP-3415 could say that a platform whose outbound requests refuse the ranges it names meets its delivery-time MUST,** which both runs support.

## Collections

- **R18.** A `uri` target covers that resource and its sub-resources. A delivery for a sub-resource names the sub-resource's own `uri`. A collection's own contents change only as its members do, so a server delivers its members' changes and nothing for the collection itself.
- **R19.** A `uriTemplate` target covers every resource whose URI matches the template, and their sub-resources. A simple `{name}` expression matches exactly one path segment, and a reserved expansion `{+name}` matches one or more characters, slashes included. RFC 6570 defines expansion, not matching, so a server MAY refuse a template with any other expression, with `Unsupported` and `data` `{"feature": "uriTemplate", "value": ...}`.
- **R20.** A `listed: true` target covers every resource `resources/list` returns to the subscription's principal.
- **R38.** A collection is a resource whose `resources/read` returns its members as entries with URIs of their own. Which of its URIs are collections is the server's to decide, and a subscription's kind MUST NOT change during its life, whatever its number of members. A `uriTemplate` or `listed` target is always a collection.
- **R39.** For a collection, a server MUST deliver only the members the principal may read, and MUST end the subscription, with SEP-3415's `terminated` envelope, only when the principal may read none of them, or, for a `uri` target, may no longer read the collection itself. The prototype does not exercise this or SEP-3415's re-verification, since everyone may read A's notes, and builds no revocation only to trigger it.
- **R32.** For a collection, the result MUST carry a `cursor`, and any subscribe call, a first one or a refresh, MAY name the `cursor` of an earlier result. The result's `changes` MUST then hold every covered resource whose newest version came after that cursor, once each and at its newest version, as a `ResourceChange` in the form the request's `catchUp` names, with a deleted one as R11 delivers it. Without a cursor, `changes` MUST hold every covered resource that exists. A client SHOULD name the cursor of its last result on every refresh.
- **R33.** A delivery MUST NOT carry a cursor, since deliveries may overlap and arrive out of order.
- **R34.** When a server can no longer tell which covered resources changed after the named cursor, it MUST answer as though none were named, and set `reset: true`. A client that receives `reset: true` MUST treat as deleted every resource it holds under the target that no page of the reset lists. A server MUST NOT answer a stale cursor with an error.
- **R35.** A server MAY split `changes` across results. A result that stops partway MUST set `hasMore: true`, with a `cursor` that resumes where it stopped, and a client SHOULD refresh again with that cursor until a result arrives without `hasMore`.
- **R36.** A server MAY make cursors and versions one value, stamped from one ordered counter. A client MUST NOT rely on that: it compares versions only for equality, and passes a cursor back unchanged.

## Who may subscribe

- **R22.** Both methods MUST be called with an authenticated principal, as SEP-3415 defines it. A server MUST refuse, with `Forbidden`, a principal that may not read the resource a `uri` target names. For a collection, it filters the members instead (R39).
- **R25.** A server MUST derive a subscription's `id` from its key with a keyed hash, so that a logged `id` cannot confirm a guessed principal (N3).

## The `patch` form

- **R42.** A server MAY declare `patch` among its forms. A change in the `patch` form carries `fromVersion`, the version it starts from, and `mergePatch`, an RFC 7396 merge patch from that version's contents to the new `version`'s. A server MUST use it only for a resource whose `contents` is one `application/json` text entry, and patches the parsed value. It MUST send the change in the `full` form instead when the new value holds a `null` as an object's member, outside any array, since a merge patch reads that as a deletion and replaces an array whole. A patch whose body would pass the bound in R27 goes as `notify`, as `full` does.
- **R43.** A delivery in the `patch` form MUST start from the version the receiver holds, which the server takes to be the resource's version before the change, unless it replaces a delivery not yet made for the same subscription and URI (R12). Then the receiver holds what it held before that one, since it never got it, and a resource that one created it does not hold at all. When a delivery out at the time gets through instead, the server MUST start from that delivery's version. When the receiver holds no version, or the server no longer keeps it, the server MUST deliver the `full` form.
- **R44.** A result with `catchUp: "patch"` MUST patch one resource from the `version` the client names, and each member of a collection from its version at the cursor. It MUST carry the contents instead, as `full` does, when the client names no version, when the server no longer keeps it, or when a member did not exist at the cursor.
- **R45.** A client MUST apply a patch only to the version its `fromVersion` names. A client that holds another SHOULD refresh a resource it subscribed to by `uri`, and SHOULD read a collection's member again, by `resources/read` or `GET`, rather than refresh with the cursor, since deliveries may have moved it past the cursor's version.
- **R46.** The field `mergePatch` names its format, as RFC 7396's media type `application/merge-patch+json` does, so that an RFC 6902 JSON Patch could arrive later as `jsonPatch`.

## Pending

- **The methods' prefix.** `resources/` belongs to the core specification, so the PR asks the working group whether an extension's methods want a prefix of their own.
- **The `_meta` key** under which `resources/read` carries a resource's version (R47), to be agreed with the Filesystems working group, with the Transports working group's Definition Tags in view. The prototype uses `io.modelcontextprotocol/resource-webhooks.version`, since MCP's rules for a key give its prefix dot-separated labels, which cannot hold the slash in the extension's identifier.
- **A read's `ttlMs` and a delivery's version,** for the PR: a positive `ttlMs` lets a cache serve a read older than the version a `notify` named, so a server should give a subscribable resource `ttlMs: 0`.
- **Two gaps inherited from SEP-3415:** which base64 alphabet the secret uses, and whether a result should also return the granted TTL, since `refreshBefore` is a clock time and a client's clock can be skewed.
- **Whether one delivery in flight per URI keeps a busy collection's deliveries flowing,** a question for the PR, since the prototype has no such load (R12).
- **R13's order holds at a receiver only within its freshness window.** A receiver that checks `webhook-timestamp`, as SEP-3415 asks, refuses a captured delivery replayed after five minutes, and one that drops a repeated `webhook-id` refuses it within them. A receiver that does neither could be rolled back to an older version, since versions compare only for equality.
- **A flood SEP-3415 leaves open, for the PR.** Through the allowlist, out-of-band verification or the receiver's well-known document, a principal can aim deliveries at a receiver that never held its secret. The receiver can only reject them, and SEP-3415 retries a rejection, suspends only after a sustained failure rate, and lets a refresh reactivate the subscription. A rule closes it: a receiver answers a delivery it cannot verify with `401`, and a server treats that as consent withdrawn, stops delivering, and forgets its verification for `(principal, url)`, so the next subscribe needs a handshake the receiver can refuse.

## Out of scope, to list in the SEP

- **Polling.** A client polls an `https` resource with a conditional `GET`, and any other with `resources/read`.
- **Delivery over an open stream,** as SEP-3415's `events/stream` offers for events, until `subscriptions/listen` opens its filter to extensions, as proposed on SEP-3415's thread.
- **How a gateway reaches its client.** SEP-3415 leaves that channel to the endpoint, and so does this extension.
- **A mirror,** where a subscriber keeps copies at the server's versions and serves them to readers of its own. It needs nothing from this extension that a client does not, and is not covered for now.

## Findings

What building the prototype teaches, one entry for each item of the master plan's § *What building it should teach us*, filled in as the build answers them. The PR's proposal carries them.

- **A version in level 1's `data` would still leave a client most of level 2 to build.** It would let a client skip a delivery naming the version it holds (R15), and nothing more. A level 1 occurrence carries no contents, as SEP-3415's payload minimality asks, so every change still costs a `resources/read`. A's `mcp.resource.updated` keeps no history, so its `cursor` is `null`, and a client back from an absence must read every resource it watches, where level 2's refresh names the version or cursor held and gets only what changed (R32). A collection's catch-up, its pages and its reset (R32 to R35) have no counterpart. Coalescing is the one piece Events could take on, since Peter agreed an event type may coalesce (N1), though A's level 1 delivers every occurrence.
- **Level 2 reuses level 1's webhook code, B included, and adds to the queue only what the `patch` form needs.** The handshake and its cache, the token bucket per host, signing, the retry schedule and its bounds are one module, and one table holds both levels' subscriptions, so one principal's cap counts both. The queue's slot is the caller's choice: level 1 gives each message its own, and level 2 keys a slot by subscription and URI, which is all R12's coalescing took. The `patch` form added three optional fields to a queued message, the version it delivers, the version the receiver holds before it, and a way to rebuild it (R43). B's delivery path has not changed since level 1.
- **A resource with no `ETag` gets its version in each read entry's `_meta`, and that is enough for a `notify` client.** A serves its lists a second way, as `lists:///inbox/groceries`, which only `resources/read` reaches, and each entry names its version under R47's key. A write to that list delivers `notify` under the URI the subscription named, with the version a quiet read then returns, so the client can tell whether it read the delivered version or a later one. A puts the version on every read it serves, `https` included, since a client that reads an `https` note through MCP has no `ETag` to compare either.
- **One or more path segments beyond the subscribed URI served as the rule for a sub-resource (R18).** A's folders nest to any depth, a write to `inbox/sub/note-1` reaches a subscription to `inbox`, and writes to `inbox-old/` and `inbox2/` do not, since the rule compares whole segments. A has no resource whose parts are not path-nested, so whether a server needs another rule, for a query string or a fragment, stays open.
- **Template matching needs `{name}` and `{+name}` only, and a server must match in time linear in the URI (R19).** A matches `.../server/A/{type}/archive` and `.../notes/{+path}/archive` against every write, RFC 6570's dotted names included, and answers any other expression, or an unmatched brace, with `Unsupported`. A first version compiled each template to a regular expression, and a principal could subscribe a template such as `.../notes/{+a}{+b}{+c}{+d}!` whose match against a 400-character path backtracked for 1.5 seconds, and five times that with one more expression, inside the write that tested it. A matcher that walks every position in the template at once takes the URI's length times the template's.
- **`listed` covers what `resources/list` returns, and should stay that way.** A lists the inbox's notes and every list, so an archived note is reachable only through a template, and a `listed` subscription hears nothing of it. Widening `listed` to everything a template reaches would make it "everything readable", which a template target with `{+path}` already offers a client that wants it, and would stop `listed` meaning what a client sees when it lists.
- **Refreshing every subscription on reconnect is enough for a client behind a gateway, and a client must refresh anyway.** While `b` is away, B answers `503` and A retries within its window, so a short absence loses nothing, and past the window the refresh names the version or cursor held and catches up (Scenarios 7 and 10). B keeps a client's secret only with its socket, so a reconnecting client registers a new secret and must refresh each subscription to name it. The demo page's `b` does so, and a restart of the Worker, which drops every socket, cost it no change. B saying what it could not pass on, as Lumenize's Gateway tells a reconnecting client `subscriptionRequired`, would add nothing those refreshes do not. A client watching many resources pays one request per subscription per reconnect.
- **A merge patch serves a resource whose contents are one JSON value, and an array in it goes whole.** A patches one `application/json` text entry and sends anything else, several entries or another type, in the `full` form (R42). Measured in the lane on 2026-10-26, a delivery for a note whose `done` changed is 143 bytes as `notify`, 416 as `full` and 190 as `patch`. For a list of 100 items with one item changed it is 137, 1600 and 1183, since RFC 7396 replaces an array whole, so the list's patch carries every item, and saves little more than what `full` spends escaping the value as a string and naming its version in `contents[0]`. A value that keeps its members in an object keyed by id, rather than an array, would patch one member at a time.
- **Both levels follow SEP-3371's extension rules as the prototype reads them, with the methods' prefix still open.** Neither sends anything on a core stream: A declares Events with an empty settings object, so level 1 adds nothing to `subscriptions/listen`, and level 2 delivers only by webhook. Neither allocates an error code, since both use SEP-3415's (R29). The metadata level 2 adds to a core type, a read entry's version, sits in `_meta` (R47). What the rules do not settle is the methods' names: `resources/webhooks/subscribe` sits under `resources/`, which the core specification owns (§ *Pending*).
- **The race B's acknowledgement guards against did not happen on Cloudflare in 16 tries.** `b` sent its secret on its socket and subscribed at once, in two runs of eight, and each time B held the secret before A's challenge arrived. In the vitest lane it showed only for a POST sent straight to B, never for a subscribe. The acknowledgement stays, since it is what guarantees the order.
- **A Worker deployed without `global_fetch_strictly_public` still delivers A's POST to B on its own `workers.dev` host.** Cloudflare's docs give error 1042 when a Worker "tried to fetch from another Worker on the same zone" without the flag, and say that otherwise such a request goes to the zone's origin rather than to a Worker. A's fetch reaches the same Worker on its `workers.dev` host, which neither sentence names, and Scenario 2 passed against such a deploy twice on 2026-10-25, as a Lumenize measurement had seen for a Durable Object. `npm run deployed -- --without-strict-public` repeats it. The flag stays, so a delivery to B goes out through Cloudflare's front door like one to any receiver.
- **Sri's Events suites, run against level 1 on 2026-10-25, as a check rather than a gate.** `conformance` #521 at `23c7c2d2f8` grades a server and #541 at `095a156277` a client. Both grade SEP-3415 at `2ec39b9c`, of 2026-10-16, a week before the `b0efd11` that level 1 follows, which separated `webhook-id` from `eventId`. They ran from a checkout, the server suite against the conformance build of A under `wrangler dev`, the client suite against `scripts/conformance-client.mjs`.
  - **What passed.** 11 of the 14 rows of `events-discovery`, and `Unsupported` for `events/stream` on a type without `push`. Of the client's, every row of `events-client-webhook`, and `events-client-no-extension`.
  - **Every poll and push row went ungraded,** on the server and the client, since `mcp.resource.updated` is delivered by webhook only. The suite probes `NotFound` for an unknown event name only through `events/poll`, so a server with no polled type is never graded on it, though A answers `events/subscribe` for an unknown name with `-32023` and `data.kind` `event`.
  - **The `notifications/events/list_changed` rows went ungraded,** since A declares Events with an empty settings object and serves no `subscriptions/listen`.
  - **No row of `events-webhook` or `events-webhook-delivery` was graded, the two SSRF rows included.** The suite's server runner cannot send a token, and the conformance build opens A's methods to it but never a subscribe, since a subscription makes A POST wherever it names. So every `events/subscribe` answers `401`, which the suite also reports as a response that is not JSON-RPC. A run with `events/subscribe` opened got no further: the scenarios subscribe with callbacks under `https://conformance.invalid`, which nothing can reach, and A sends its handshake while it handles `events/subscribe`, as SEP-3415 describes, so every subscribe failed with `CallbackEndpointError`. The delivery rows would also need `EVENTS_WEBHOOK_CALLBACK_BASE`, a public `https` URL forwarded to the suite's receiver. Grading these rows needs a token for the suite, and a callback the server can reach.

## Withdrawn

- **R9** (a MUST to end a subscription whose principal can no longer read what it covers), withdrawn 2026-10-25 in favour of SEP-3415's § *Authorization*, which R17 takes by reference, and R39.
- **N5** (a receiver's `410` stops one version), moved 2026-10-25 into R17's substitutions, since it follows from R14 and SEP-3415's `410` rule.
- **N2 and R24** (verification cached per `(principal, delivery.url, delivery.secret)`), withdrawn 2026-10-25: a verified principal can point a URL at any number of targets with no new handshake either way, and a challenge on rotation would fail a stock Events receiver.
- **R21** (a version for a whole collection), withdrawn 2026-10-25 when a collection's catch-up came to name a cursor.
- **R23** (callers without credentials share one anonymous principal), withdrawn 2026-10-20 when subscribing came to require an authenticated principal.
